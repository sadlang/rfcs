- **الحالة:** مقبول → قيد التنفيذ (أقرّه المالك 2026-07-25). **✅ F2-أ مكتملة ومدموجة** (#277، السمة + راية AST + قبول المحرّكين). **✅ F2-ب مكتملة** (تخطيط LLVM بلا ترويسة + محاذاة/حجم C آليّ 24→16 بايت): بنية `@تمثيل_سي` تُصدَّر `{ i64, i64 }` بدل `{ ptr, i64, i64 }`، فالحقل 0 عند الإزاحة 0 (مطابقٌ لـ`struct { long; long; }` في C). مبرهَنة حيًّا: دالّة `memset` خارجيّة تصفّر أوّل 8 بايتات ⇒ الحقل الأوّل يصير 0 (عند الإزاحة 0)؛ الضبط بترويسة ⇒ يبقى سليمًا. **حارس أمان (مراجعة أميليا C-1):** بنية `@تمثيل_سي` لا تُبنى لها vtable ⇒ استدعاء طريقة عليها إرسالٌ مباشر (لا يُقرأ الحقل 0 كمؤشّر vtable). **✅ F2-ج مكتملة (تمرير/إرجاع بالقيمة، تصنيف ABI System V AMD64 / Windows x64):** بنية `@تمثيل_سي` في توقيع `دالة خارجية` تُمرَّر/تُرجَع **بالقيمة ضمنًا** (قرار المالك 2026-07-25)؛ التمرير بالمؤشّر يبقى صريحًا عبر `رقم`. مبرهَنة بدليلين: IR مطابقٌ لـClang للهدفين (Win64: سجلّ/‏byval/‏sret؛ SysV: قطعتا `{i64,i64}`)، وربطٌ وتشغيلٌ حيٌّ Win64 (ص تنادي دوالّ C بالقيمة ⇒ `107/42/42/42`). **بذا اكتمل الحاجز الثالث (FFI بنيويّ) بمراحله الثلاث.** التمرير بالمؤشّر المؤنمَط (`ptr` بدل `i64`) للأنواع العدديّة يبقى دَينًا مؤجَّلًا مقبولًا (يعمل بتطابق عرض المؤشّر على x86-64).

> **⚠️ تنبيه تشخيص مبكِّر (اقرأ أوّلًا):** أُعِدَّ هذا المقترح بعد **فحص تجريبيّ مباشر بدليل
> LLVM-IR** لحالة تمرير بنية عبر حدّ C في المترجم الحاليّ. النتيجة المفاجئة: **تمرير البنية
> يعمل ميكانيكيًّا بالفعل** — المؤشّر يعبر الحدّ وتُعدِّل دالّة C ذاكرةَ كومة ص فعليًّا. لكنّ
> الحاجز الحقيقيّ ليس «تمرير المؤشّر» بل **تخطيط ذاكرة بنية ص**: كلّ بنية/صنف في ص مُعلَّبة على
> الكومة بـ**ترويسة صنف مخفيّة (مؤشّر) عند الإزاحة صفر**، فتُصبح حقولها مُزاحةً ٨ بايت عن بنية C
> خالصة ⇒ **بنى ص ليست متوافقة تخطيط-ABI مع C**. لذا جوهر هذا المقترح تخطيطيّ لا آليّة تمرير:
> إتاحة **بنية بتخطيط قيمة C-متوافق** (بلا ترويسة) للربط الخارجيّ.

# ملخّص

يقترح هذا المقترح **نوع بنية بتخطيط ذاكرة متوافق مع C-ABI** يُستعمل في الربط الخارجيّ
(`دالة خارجية`). حاليًّا كلّ `بنية`/`صنف` في ص مُعلَّبة على الكومة مع ترويسة صنف مخفيّة عند
الإزاحة صفر، فلا يطابق تخطيطُها بنيةَ C المقابلة (`struct { long س; long ص; }`). النتيجة أنّ
دوالّ C التي تقرأ/تكتب حقول بنية عبر الحدّ ترى حقولًا **مُزاحةً**، ما يجعل FFI البنيويّ الحقيقيّ
(بنى بالقيمة، مؤشّرات مؤنمَطة، تشارُك ذاكرة مع C) **غير سليم دلاليًّا** رغم عمله بمصادفة تسجيل
على x86-64.

المقترَح: **سمة `@تمثيل_سي`** (أو مكافئها الّذي يُحسَم في «الأسئلة غير المحسومة») تُعلِّم `بنية`
بأنّها يجب أن تُخطَّط كبنية C خالصة — **بلا ترويسة، بتخطيط قيمة، بحقول متجاورة بمحاذاة C**.
**النتيجة المرئية للمستخدم:** يمكن تمرير/استقبال بنى بين ص وC بأمان تخطيطيّ، وهو حجرُ الأساس
للاستضافة الذاتيّة إن اختِير مسارٌ يتقاطع مع libLLVM أو مكتبات C بنيويّة، ولمنظومة ص السياديّة
(nahla، sad-os) الّتي تتفاعل مع بنى العتاد/النظام.

# الدافع (Motivation)

خارطة الاستضافة الذاتيّة (RFC خارطة الطريق، الحاجز ٣) تعزل **FFI البنيويّ** كوحدة عمل: «توسيع
FFI للبنى بالقيمة والمؤشّرات وردود النداء». الفحص التجريبيّ (٢٠٢٦-٠٧-٢٥) يحسم أنّ:

- **آليّة تمرير المؤشّر تعمل:** برنامج ص يمرّر بنيةً إلى `دالة خارجية("memset")`، و`صفّر(ن، 0، 24)`
  يُصفّر ٢٤ بايتًا من ذاكرة كومة ص فعليًّا (البرنامج المترجَم يطبع `111` ثمّ `0`). المؤشّر يعبر
  الحدّ، وC يعدّل ذاكرة ص.
- **لكنّ التخطيط غير متوافق:** بنية `نقطة { رقم س؛ رقم ص }` تُولَّد في LLVM كـ
  `{ ptr ترويسة، i64 س، i64 ص }` (malloc 24)، فحقلُ `س` عند الإزاحة **٨** لا **٠**. برهان:
  `صفّر(ن، 0، 8)` يُصفّر **الترويسة** لا `س` (تبقى `س = 111`). أيّ دالّة C تتوقّع
  `struct { long س، ص }` ستقرأ الترويسة مكان `س`.

بدون بنية متوافقة-C، يبقى كلّ FFI بنيويّ **إمّا خاطئًا تخطيطيًّا (تمرير بنية ص خامًّا)، أو يدويًّا
مؤلمًا (تفكيك الحقول إلى معاملات عدديّة وإعادة تجميعها)**. حالات الاستخدام الواقعيّة:

- **nahla / sad-os:** التفاعل مع بنى النظام (`timespec`، `stat`، واصفات العتاد) يتطلّب تخطيطًا
  مطابقًا للـABI.
- **الاستضافة الذاتيّة:** أيّ جسرٍ مستقبليّ إلى مكتبة C بنيويّة (بما فيها libLLVM إن أُعيد النظر
  في مساره) يتطلّب تمرير بنى/مقابض بتخطيط سليم.
- **مكتبات C عامّة:** استدعاء `gettimeofday`, `stat`, `ioctl`… يتطلّب بنى بالقيمة/بالمؤشّر
  متوافقة تخطيطيًّا.

# الشرح التوجيهي (Guide-level explanation)

اليوم تُكتب البنية هكذا وتُعلَّب مع ترويسة صنف مخفيّة (تُمكّن الطرائق/التعدّديّة الشكليّة):

```sad
بنية نقطة
    رقم س = 0
    رقم ص = 0
نهاية
```

للربط الخارجيّ نضيف سمة تُصرِّح أنّ هذه البنية **بيانات صرفة بتخطيط C** (لا ترويسة، لا طرائق
افتراضيّة):

```sad
@تمثيل_سي
بنية وقت_س
    رقم ثوانٍ = 0
    رقم نانو = 0
نهاية

# `clock_gettime` تكتب في بنية المتّصِل عبر **مؤشّر** (المعامل الثاني `struct timespec *`)،
# فنمرّره صراحةً بوصفه `رقم` (عنوانًا) — لأنّ بنية `@تمثيل_سي` في التوقيع تعني «بالقيمة» ضمنًا.
دالة خارجية("clock_gettime") رقم اقرأ_الساعة(رقم، رقم)

متغير ت = وقت_س()
اقرأ_الساعة(0، عنوان(ت))    # نمرّر عنوان البنية (رقم) ⇒ C يكتب الحقول في ذاكرة ص بتخطيط سليم
اطبع_سطر(ت.ثوانٍ)          # يقرأ قيمةً صحيحة (لا مُزاحة)

# ومثالُ التمرير/الإرجاع **بالقيمة** (F2-ج): بنية `@تمثيل_سي` مباشرةً في التوقيع.
دالة خارجية("point_sum") رقم مجموع(نقطة)      # نقطة (16 بايت) تُمرَّر بالقيمة (byval/قطعتان)
دالة خارجية("make_point") نقطة اصنع()          # وتُرجَع بالقيمة (sret أو {i64,i64})
```

الفكرة الذهنيّة للمستخدم: **`@تمثيل_سي` = «هذه البنية عقدٌ ثنائيٌّ مع C»**. تفقد قدرات ص
الكائنيّة (الترويسة/الطرائق الافتراضيّة/التعدّديّة) مقابل **تخطيطٍ مضمونِ التوافق**. البنى
العاديّة (بلا السمة) تبقى كما هي تمامًا — لا تغيير كاسر.

قواعد التشخيص المتوقّعة:

- استعمال بنية غير `@تمثيل_سي` في توقيع `دالة خارجية` بوصفها **بنيةً بالقيمة** ⇒ تحذير/خطأ
  موجِّه: «مرّرها كمؤشّر، أو علّمها `@تمثيل_سي`». **🟠 دَينٌ تشخيصيّ مؤجَّل بعد F2-ج (مراجعة أميليا #3):**
  حاليًّا بنيةٌ غير-`@تمثيل_سي` بالقيمة في توقيع خارجيّ **تنحطّ صامتةً** إلى مؤشّر/‏`i64` (السلوك الموروث
  قبل F2-ج، غير كاسر). ترقيتُه إلى خطأٍ صريح = **قرار دلاليّ للمالك** (ما معنى بنيةٍ غير-C بالقيمة في FFI؟)
  ولا يُتّخَذ من طرفٍ واحد كي لا يُكسَر أيّ استعمالٍ موروث يعامل معامل الصنف مؤشّرًا معتِمًا.
- حقلٌ من نوع غير-متوافق-C (مصفوفة ديناميّة، نصّ ص، خريطة) داخل `@تمثيل_سي` ⇒ خطأ: «حقل غير
  متوافق مع تخطيط C». **قيدٌ متأصّل بالـFFI (أميليا #1/#2):** حقول `@تمثيل_سي` تتبع أحجام أنواع ص —
  `رقم` = 8 بايت (⇔ C `int64_t` حصرًا، لا `int`)، `عشري` = `double` — فيجب أن يطابقها إعلان C 64-بت؛
  والبنى المتداخلة/المصفوفات الداخليّة غير مدعومة بعدُ (تُخزَّن مؤشّرًا في ص فتفسد بالقيمة).

# الشرح المرجعي (Reference-level explanation)

- **مصدر الحقيقة (`language-truth/`):**
  - سمة/توجيه جديد `@تمثيل_سي` في `grammar/` (على الأرجح امتداد لقواعد السمات/المزخرِفات
    القائمة في `60_advanced` أو `20_declarations`). يُحسَم الاسم النهائيّ في الأسئلة.
  - رمز خطأ جديد في `errors/` لِـ«حقل غير متوافق مع تخطيط C» و«بنية غير-C بالقيمة في FFI».
  - رفع الملاحظة إن اقتضى: تفاعل السمة مع `صدّر بنية` (المُغلَق حديثًا، ISSUE-026).
- **المحلل المعجمي/النحوي (Lexer/Parser):** إن اختِيرت صياغة سمة `@`، يُعاد استعمال بنية
  المزخرِفات القائمة؛ لا رمز معجميّ جديد جوهريّ. إن اختِيرت كلمة مفتاحيّة (`بنية_سي`) فرمزٌ
  محجوز جديد (تكلفة أعلى).
- **الشجرة المجردة (AST):** راية `isCRepr` (أو ما يكافئها) على عقدة `StructDecl`
  (`declarations.h`). لا عقدة جديدة.
- **المفسّر:** التخطيط لا يُلاحَظ في المفسّر مباشرةً (لا FFI بنيويّ حقيقيّ فيه)، لكن يجب أن
  **يقبل** السمة دون خطأ ويحافظ على دلالة القيمة نفسها (تكافؤ محرّكين).
- **المترجم (sadc):** الجوهر. عند بناء نوع LLVM للبنية `@تمثيل_سي`:
  - **حذف ترويسة الصنف** (`{ptr, …}` ⇒ `{…}` فقط) — الحقول من الإزاحة صفر.
  - محاذاة/حشو حسب قواعد C-ABI للهدف (System V AMD64 مقابل Windows x64).
  - في `astTypeToSIRType`/codegen التصريح الخارجيّ (`cf_branch_call.cpp:336`): إصدار نوع
    LLVM سليم (`ptr` للتمرير بالمؤشّر؛ ونوع البنية للتمرير بالقيمة حسب تصنيف ABI: sret/byval/
    تقسيم سجلّات).
  - **تخصيص التخزين:** بنية `@تمثيل_سي` قد تُخصَّص على المكدّس (alloca) لا الكومة (malloc)
    حين لا تتطلّب عمرًا كائنيًّا — قرار تنفيذ.
- **نظام الأخطاء:** رمزان جديدان على الأقلّ (حقل غير متوافق؛ استعمال بنية غير-C بالقيمة في FFI).
- **الأدوات:** LSP يعرض السمة؛ المنسّق يحافظ عليها؛ sadinfo يوثّق القيد.
- **التوافق الخلفي:** **إضافة غير كاسرة** — البنى القائمة (بلا السمة) لا تتغيّر إطلاقًا. السمة
  اختياريّة صرفة.

**التدرّج المقترَح للتنفيذ** (بعد القبول، كوحدات claim منفصلة):
1. ✅ **F2-أ (مكتملة، #277):** السمة + الراية في AST + قبول المفسّر (تكافؤ محرّكين، بلا سلوك جديد).
2. ✅ **F2-ب (مكتملة):** تخطيط LLVM بلا ترويسة + محاذاة/حجم C آليّ (`getTypeAllocSize`، 24→16 بايت).
  البرهان الذهبيّ محقَّق: دالّة `memset` خارجيّة تصفّر أوّل 8 بايتات فيصير الحقل الأوّل 0 (عند
  الإزاحة 0) — دليلٌ مباشر أنّ التخطيط صار C-متوافقًا. حارس C-1 (لا vtable لبنية C-repr ⇒ إرسال
  مباشر للطُّرق). تمرير المؤشّر المؤنمَط (`ptr` بدل `i64`) أُجِّل كدَين مقبول (يعمل بتطابق العرض).
3. ✅ **F2-ج (مكتملة):** تمرير/إرجاع بنية **بالقيمة** حسب تصنيف ABI للهدف (System V AMD64 / Windows x64).
  **قرار المالك (2026-07-25):** بنية `@تمثيل_سي` في توقيع `دالة خارجية` = **بالقيمة ضمنًا**؛ التمرير
  بالمؤشّر يبقى صريحًا عبر `رقم` (كما في الاستعمال القائم `memset`/`clock_gettime`) ⇒ غير كاسر.
  **التنفيذ (٨ ملفّات، +488 سطر):** (أ) `SIRFunction.isExtern + returnClassName` يُنقَلان من `FunctionDecl`؛
  (ب) مصنِّف ABI `classifyCReprAbi`: **Win64** حجمٌ ∈ {1,2,4,8} ⇒ سجلّ عدديّ واحد `iN`، وإلّا `byval`
  مؤشّر؛ العائد ≤ 8 ⇒ مباشر في RAX، وإلّا `sret`. **SysV** بنية ≤ 16 بايت ⇒ قطعة/قطعتان «ثمانيّة»
  (كلّها عشريّة ⇒ `double` في XMM، وإلّا `iN` في GPR)، > 16 ⇒ `byval` ذاكرة؛ العائد ≤ 16 ⇒ مباشر
  (نوعٌ مفرد أو `{i64,i64}`)، وإلّا `sret`. (ج) `emitFunctionPrototype` يحسب `CReprCallPlan` مرّةً
  (تصاريح-أوّلًا) ويطبّق سمتَي `byval`/`sret` على **التصريح**؛ (د) موقع النداء يقرأ الخطّة، يحمّل قطع
  البنية من ذاكرة الكائن، يخصّص عائد `sret`، يجسّد العائد المباشر، ويطبّق السمتين على **النداء** (يلزمهما
  LLVM في الموضعين). (هـ) إصلاح المحلّل: `parseExternFunctionDecl` كان يقبل نوع العائد المبنيّ فقط لا
  اسم صنفٍ مُعرَّف ⇒ أُضيف إرشاد الرمزين المتتاليين (مطابقًا للدالّة العاديّة).
  **البرهان المزدوج:** (١) **IR مطابقٌ لـClang** للهدفين — Win64: `small_sum(i64)` / `make_small()→i64`
  / `point_sum(ptr byval)` / `make_point()→void … sret`؛ SysV: `point_sum(i64,i64)` /
  `make_point()→{i64,i64}`. (٢) **ربطٌ وتشغيلٌ حيٌّ Win64:** برنامج ص ينادي دوالّ C حقيقيّة تمرّر/تُرجِع
  `@تمثيل_سي` بالقيمة (بنية 8 بايت في سجلّ + بنية 16 بايت عبر `byval`/`sret`) ⇒ الخرج `107/42/42/42`
  صحيحٌ طرفًا لطرف. LLVM يضمن توليد الشِّفرة الآليّة المطابقة للـABI من IR الصحيح (byval/sret/تقسيم القطع).

# السلبيات (Drawbacks)

- **تعقيد ABI:** التمرير بالقيمة يتطلّب تصنيف System V AMD64 / Windows x64 (سجلّات مقابل ذاكرة،
  sret، byval) — منطقٌ حسّاس للهدف وعالي الصيانة. لذا التدرّج يفصل «بالمؤشّر» (سهل) عن
  «بالقيمة» (صعب).
- **ازدواج مفهوميّ:** نوعان للبنية (كائنيّة مقابل C) قد يربك المستخدم.
- **قيود تخطيط C:** لا حقول ديناميّة (نصّ ص/مصفوفة/خريطة) داخل `@تمثيل_سي`؛ قيدٌ يجب توثيقه
  بوضوح.
- **مخاطرة انحدار FFI القائم:** مستعملو FFI الحاليّون (مكدّس شبكة nahla، أغلفة libc) يعتمدون
  على تمرير المؤشّر كـi64؛ أيّ تغيير في codegen التواقيع يلزمه حارس انحدار كامل. (هذا يخصّ مسار
  F1 المؤنمَط لا F2 مباشرةً، لكنّه يتقاطع.)

# المبرّرات والبدائل (Rationale and alternatives)

- **لماذا سمة لا نوع منفصل؟** السمة إضافة غير كاسرة تُعيد استعمال بنية المزخرِفات، وتُبقي
  `بنية` مفهومًا واحدًا. البديل `بنية_سي` ككلمة محجوزة أثقل معجميًّا وأكثر تفرّعًا.
- **بديل «التمرير بالمؤشّر فقط، بلا تخطيط-C»:** يترك الحقول مُزاحةً ⇒ لا يحلّ الحاجز الحقيقيّ.
- **بديل «التفكيك اليدويّ» (تمرير كلّ حقل معاملًا عدديًّا):** يعمل اليوم لكنّه هشّ، لا يقيس،
  ولا يدعم بنى الإخراج (out-params).
- **بديل «عدم فعل شيء»:** مقبول إستراتيجيًّا لأنّ RFC خارطة الطريق يصنّف الحاجز ٣ **«مؤجَّل لا
  حاجز»** لمسار IR النصّيّ. هذا المقترح يُفعَّل فقط إن قرّر المالك المضيّ في FFI البنيويّ.

# أعمال سابقة (Prior art)

- **داخل المستودع:** مقترح «بدائيّة تحميل/تخزين عبر مؤشّر خامّ» (فرع `rfc/f3-raw-pointer-load-store`)
  يعالج `ذاكرة_اكتب`/`ذاكرة_اقرأ` عبر مؤشّر خامّ — مكمّلٌ لكن متمايز: ذاك بايتات خام، وهذا
  **تخطيط بنية مؤنمَط**. و«تصريح خارجيّ» (`rfc/extern-postfix-adjective`) يخصّ صياغة `دالة خارجية`.
- **Rust:** `#[repr(C)]` — النموذج المرجعيّ المباشر: يُوقف تحسين تخطيط Rust ويفرض تخطيط C. سمتُنا
  `@تمثيل_سي` مكافئها العربيّ.
- **C#/.NET:** `[StructLayout(LayoutKind.Sequential)]` + P/Invoke marshalling.
- **Go:** `cgo` مع بنى C صريحة (`C.struct_...`).
- **Dart:** `dart:ffi` مع `Struct` subclasses ذات تخطيط ثابت.

الدرس المشترك: **فصل تمثيل البيانات الكائنيّ عن تمثيل الـABI صراحةً** بسمة/إعلان، لا محاولة جعل
كلّ بنية متوافقة تلقائيًّا (يكسر ميزات اللغة الكائنيّة).

# أسئلة غير محسومة (Unresolved questions)

- **الصياغة:** سمة `@تمثيل_سي`، أم كلمة `بنية_سي`، أم عبارة `بنية خارجية`؟ (قرار المالك.)
- **التسمية العربيّة:** «تمثيل_سي» مقابل «تخطيط_سي» مقابل «ثنائيّ_سي». (RFC 0034 تطابق الصفة.)
- **نطاق المرحلة الأولى:** هل نكتفي بالتمرير بالمؤشّر (F2-ب) ونؤجّل بالقيمة (F2-ج)؟
- **المحاذاة الصريحة:** هل نضيف `@محاذاة(N)` لاحقًا، أم نلتزم محاذاة C الطبيعيّة فقط الآن؟
- **الهدف الحرّ:** كيف تتفاعل السمة مع الوضع الحرّ (nahla/sad-os) وبنى العتاد ذات المحاذاة الخاصّة؟
- **خارج النطاق:** ردود النداء (مؤشّرات دوالّ C — F3) واتّحادات C (`union`) — مقترحات لاحقة.

# إمكانات مستقبلية (Future possibilities)

- **F3 ردود النداء:** تمرير دالّة ص كمؤشّر دالّة C (`qsort`، معالِجات).
- **اتّحادات C** (`@تمثيل_سي` على نوع اتّحاديّ).
- **مصفوفات C ثابتة الطول** داخل البنى (`رقم مصفوفة[8]`).
- **توليد جسور تلقائيّة** من ترويسات C (مولِّد ربط).
- **إعادة النظر في مسار libLLVM** متى نضجت البنى بالقيمة + ردود النداء (يرفع الحاجز الأصليّ الّذي
  دفع لاختيار مسار IR النصّيّ).
